1. Plan Spec Flag: preCopySourceDisks

Enables the two-phase transfer for a Hyper-V migration plan. When false (default), the legacy flow is used (virt-v2v reads directly from SMB).

    destination: { ... }

    network: { ... }
    storage: { ... }

    - id: <vm-id>
  preCopySourceDisks: true    # Enable two-phase transfer

2. SMB Multichannel Configuration

Multichannel is optional but recommended for performance. It spreads SMB reads across all available NICs. The two-phase flow's sequential I/O pattern is ideal for multichannel, the legacy flow's random I/O cannot benefit from it.

Which NICs are used?

Multichannel uses all routable NICs on the Hyper-V server that the OpenShift worker can reach. These are the server's global/physical NICs — the same NICs visible to every VM and service on that host. They are not per-VM virtual NICs. The Linux CIFS client negotiates channels with the SMB server, and the server advertises all its network interfaces. The client then opens parallel TCP connections to each reachable interface.

Server-side (Hyper-V host) — run once per host via PowerShell
Enable multichannel Set-SmbServerConfiguration -EnableMultiChannel $true -Force
Usually enabled by default on Windows Server 2012+.
Verify status Get-SmbServerConfiguration | Select EnableMultiChannel
Exclude unreachable interfaces
(critical for clusters)		 
# List all server interfaces (including hidden ones):
Get-SmbServerNetworkInterface -IncludeHidden | ft InterfaceIndex,FriendlyName,IpAddress

# Block interfaces that OCP nodes cannot reach:
New-SmbMultichannelConstraint -ServerName * -InterfaceAlias "vEthernet (cluster-net)" -Flags Disable
New-SmbMultichannelConstraint -ServerName * -InterfaceAlias "Loopback*" -Flags Disable
Without this, the server advertises cluster-only or link-local interfaces. The client tries them, they time out, and multichannel effectively uses only 1 channel.
Verify active channels Get-SmbMultichannelConnection | ft ServerName,ClientIpAddress,ServerIpAddress
Client-side (Forklift provider settings)
Provider setting 
apiVersion: forklift.konveyor.io/v1beta1
kind: Provider
metadata:
  name: my-hyperv
spec:
  type: hyperv
  url: ...
  settings:
    smbMaxChannels: "8"    # 0 = disabled, 1-16 = enabled
How it works Forklift reads smbMaxChannels from the provider settings and adds max_channels=N to the CIFS mount options on the SMB PV. The Linux kernel's CIFS client then negotiates up to N channels with the server.
Default 0 (multichannel disabled). Set to 8 for best results with 4-8 NICs.
Single NIC? Safe to enable — CIFS falls back to a single channel automatically. No performance penalty.

5. How the Two-Phase Transfer Works

  1. Plan Controller powers off the source VM via WinRM.
  2. Plan Controller creates a deep inspection pod that mounts the VM's VHDX disks from the SMB share and runs virt-inspector to detect the guest OS, filesystems, and applications. All disk paths are passed comma-separated — virt-inspector identifies the OS disk automatically. Results are fetched via Kubernetes pods/proxy subresource.
  3. Plan Controller creates target PVC(s) with volumeMode: Block and a conversion pod with:
    • Init container (hyperv-disk-copy): mounts the SMB share at /hyperv (read-only) and gets VolumeDevices for the target block device(s) (/dev/block0, /dev/block1, etc.)
    • Main container (virt-v2v): gets the same VolumeDevices but does NOT mount the SMB share
  4. Init container runs qemu-img convert -p -f vhdx -O raw -t writeback /hyperv/vm.vhdx /dev/block0, converting each VHDX from the SMB share directly to the target block device. qemu-img understands the VHDX Block Allocation Table, so only allocated regions are written.
  5. Init container exits, then virt-v2v starts with V2V_inPlace=1. It performs guest customization (VirtIO drivers, bootloader, network fixup) directly on /dev/block0. No data copy.
  6. Plan Controller creates the KubeVirt VirtualMachine CR with the populated PVC.

Key design decision: The SMB volume is added at pod level but only mounted in the init container. virt-v2v never has access to the SMB share — it operates purely on the local block device. This prevents virt-v2v's random I/O pattern from going over SMB.
